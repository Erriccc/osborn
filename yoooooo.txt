## Osborn Project: UI & Performance Analysis

### Tech Stack (Verified)

**Frontend** — Next.js 14, React 18, Tailwind CSS 3, LiveKit Components React, react-markdown 10, rehype-highlight, Supabase. Located in `frontend/`.

**Agent** — Node.js 18+, TypeScript 5, LiveKit Agents SDK 1.0, Anthropic Claude Agent SDK, OpenAI Codex SDK, MCP SDK, Deepgram, ElevenLabs, Silero VAD. Located in `agent/`.

---

### 🔴 Critical Performance Issues

**1. Monolithic VoiceRoom.tsx — 2,203 lines, zero code splitting**
The file at `frontend/src/components/VoiceRoom.tsx` is 2,203 lines long and contains 12 sub-components inlined together: `StreamingDots`, `ReasoningBlock`, `ToolCallBlock`, `MessageBubble`, `ChatPanel`, `TextInput`, `ControlMenu`, `PermissionModal`, `StatusIndicator`, `VoiceVisualizer`, `VoiceRoomInner`, and the outer `VoiceRoom`. None of these are lazy-loaded or split. The entire 2,200-line component tree renders on first mount.

**2. Console.log calls in every hot render path**
`MessageBubble` fires `console.log` on every single render: `"🎨 Rendering MessageBubble"`. `MarkdownMessage` fires `console.log` on every render: `"📝 MarkdownMessage rendering"`. The `addMessageRef` callback fires multiple logs per message. In a live voice session with frequent state updates, this hammers the browser's console and blocks the main thread.

**3. No memoization on MarkdownMessage or MessageBubble**
`MarkdownMessage` is never wrapped in `React.memo`. Since messages are rendered in a list via `.map()`, every time a new message arrives, ALL previous message bubbles re-render, including their expensive `react-markdown` + `rehype-highlight` syntax highlighting pipeline.

**4. TypeScript strict mode is OFF**
`agent/tsconfig.json` has `"strict": false`. This means no strictNullChecks, no noImplicitAny. There are multiple `.as any` casts visible in `claude-llm.ts` (line 70 for `google.beta as any`, line 186 for `openai.realtime`) and in `smithery-proxy.ts`. These bypass type safety and mask potential runtime errors.

**5. Empty Next.js config — no performance features enabled**
`frontend/next.config.js` is literally `const nextConfig = {}`. No image optimization domains, no bundle analyzer, no experimental features, no headers, no compression config. Next.js 14 ships with several opt-in performance improvements that are all bypassed.

**6. Agent index.ts is 2,129 lines — no module separation**
The orchestration logic in `agent/src/index.ts` handles room lifecycle, voice queue, data channel messaging, session gating, MCP management, research execution, and realtime session creation all in a single flat file. The `executeResearch` function is nested inside `createRealtimeSession`, making it inaccessible for testing or reuse.

---

### 🟡 User Interface Issues

**7. No error boundaries anywhere in the React tree**
`layout.tsx` (19 lines) has no error boundary. `VoiceRoom` has no error boundary. If `react-markdown` or `rehype-highlight` throws on malformed content (which is a real risk given raw Claude output), the entire UI crashes to a blank page.

**8. No loading state on initial page render**
`page.tsx` initializes `connectionState` as `'browsing'` and reads from `localStorage` in a `useEffect`. This causes a layout flash — the UI renders with potentially stale default values before the stored preferences are applied.

**9. Session gate mutes the mic without UX explanation**
In `VoiceRoomInner` around line 1280: `localParticipant?.setMicrophoneEnabled(false)` is called silently when sessions exist. Users see the mic muted with no visual explanation that they need to choose a session first. The only indicator is a dimmed UI — there is no explanatory banner or instructional text visible at that moment.

**10. Suggestion prompts are hardcoded and not personalized**
The `SUGGESTIONS` constant at line 339 always shows: "What files are in this project?", "Fix the TypeScript errors", "Explain this codebase", and "Run the tests." These do not change based on the active session, project contents, or time of day.

**11. Markdown detection regex is fragile**
At line 288 in `VoiceRoom.tsx`: `const hasMarkdown = /[*#\`\[\]|]/.test(part.content)`. This catches any asterisk or backtick, which means text like "don't use it" (with an apostrophe) won't trigger markdown, but "it's *important* to note" will, creating inconsistent rendering between simple spoken TTS content versus structured responses.

**12. Tailwind config has no custom tokens or theme extension**
`tailwind.config.ts` has `theme: { extend: {} }` — completely empty. The codebase uses violet-500, purple-600, blue-400, emerald-500, and amber-400 as recurring colors across dozens of components but none are defined as semantic tokens. A brand color rename would require touching 50+ class instances.

**13. No font loading configuration**
`layout.tsx` has no `next/font` import. The body falls back to `system-ui` via `globals.css`. There's no font optimization (no preloading, no `font-display: swap`), which affects First Contentful Paint on non-system fonts.

---

### 🟢 What Works Well

- The **dual voice architecture** (direct STT→Claude→TTS vs. realtime OpenAI/Gemini) is cleanly separated across `voice-io.ts`, `claude-llm.ts`, and `bridge-llm.ts` with well-defined interfaces.
- The **voice queue with 8-second debounce** in `index.ts` (line 462 `scheduleResearchBatch`) is well thought-out and prevents flooding the realtime model during active research.
- The **Smithery proxy pattern** in `smithery-proxy.ts` is an elegant workaround for the Claude Agent SDK bug with HTTP MCP transport — the reconnection patch at line 190 shows careful attention to SDK edge cases.
- The **session metadata system** in `config.ts` properly cleans up orphaned metadata, uses streaming JSONL reads to avoid loading full sessions into memory, and caps context summaries at 100 characters per message.
- The **VAD tuning** in `voice-io.ts` — `minSilenceDuration: 1.2s`, `activationThreshold: 0.65` — reflects real-world testing against false positives from ambient noise.
- The **TTS summarization** via `summarizeForTTS()` in `claude-llm.ts` correctly strips markdown and truncates at sentence boundaries before sending to TTS, preventing the model from reading `**bold**` literally.

---

### Top 5 Recommended Improvements (Prioritized)

1. **Split VoiceRoom.tsx** — Extract `PermissionModal`, `ControlMenu`, `ChatPanel`, and `MessageBubble` into separate files. Wrap `MessageBubble` and `MarkdownMessage` with `React.memo`. This is the single highest-impact change.
2. **Remove all debug `console.log` calls from render paths** — Especially in `MessageBubble` and `MarkdownMessage`. These fire on every keystroke and incoming message in production.
3. **Enable TypeScript strict mode** — Set `"strict": true` in `tsconfig.json` and resolve the resulting type errors. The `as any` casts in the LLM wrappers are likely hiding null-pointer issues.
4. **Add `React.Suspense` and error boundaries** — Wrap `VoiceRoom` and `MarkdownMessage` with error boundaries and loading fallbacks to prevent blank-screen crashes from malformed AI output.
5. **Add `React.memo` + `useMemo` to the message list** — The chat panel re-renders every message bubble when any new message arrives. Memoizing completed (non-streaming) messages would eliminate most wasted renders.

Every single `sendToAgent` call — `handleLoadSessions`, `handleResumeSession`, `handleContinueSession`, `handleMcpToggle`, `handleLoadMcpStatus`, `handlePermissionResponse`, and the file payload builder — each creates `new TextEncoder()` inline. A single module-level singleton would suffice.

## Part 1: The Current Deployment Model — What You're Working With

First, the baseline from your code. The agent today runs as a local Node.js daemon that you start manually with `npm run room <code>`. It opens a persistent WebSocket connection outbound to LiveKit Cloud for the room, and separately starts a small HTTP server on port 8741 that exposes `/sessions` and `/health`. The frontend's `SessionBrowser` component polls that local server directly — that's why the `agentUrl` field defaults to `http://localhost:8741` in `SessionBrowser.tsx`. LiveKit Cloud handles the WebRTC media relay; only your agent process runs locally.

This is fine for a personal developer tool, but it is the primary bottleneck to a cloud product. The sessions list lives on whoever's machine is running the agent. There is no authentication. Anyone with the room code can connect.

---

## Part 2: Cloud Deployment Strategy — The Two Paths

### The Core Architectural Constraint You Must Understand First

The agent worker process cannot be serverless. It maintains a persistent outbound WebSocket to LiveKit Server for its entire lifetime — that's how LiveKit dispatches room jobs to it. The moment that connection drops, the worker is unregistered. AWS Lambda, Vercel Functions, and Cloudflare Workers are all incompatible. The agent must be a long-running daemon process.

On the other hand, the agent only makes **outbound** connections — to LiveKit Cloud and to the AI APIs (OpenAI, Google, Deepgram, Anthropic). It needs no inbound ports, no public IP, no load balancer in front of it. This makes it easy to run on almost any platform that supports outbound networking.

### Path A: LiveKit Cloud Managed Agent Hosting (Recommended Starting Point)

As of 2025, LiveKit Cloud can fully host your agent worker process alongside the WebRTC infrastructure. The workflow is: write a Dockerfile for your `agent/` directory, run `lk agent deploy` via the LiveKit CLI, and LiveKit builds the container image and deploys it to their global network. They handle scaling, load balancing, rolling deployments (1-hour drain window so no active sessions are killed mid-conversation), and observability.

**Pricing:**
- Free (Build tier): 1,000 agent session minutes per month, 5 concurrent sessions. That's roughly 16 hours of agent time before you pay anything. Good enough for a beta with a small user base.
- Ship: $50/month for 5,000 minutes and 20 concurrent sessions. Overage is $0.01/minute.
- Scale: $500/month for 50,000 minutes and 600 concurrent sessions.

What counts as an "agent session minute" starts when your agent joins a room and stops when the session ends. It covers compute hosting and observability, but NOT your OpenAI, Deepgram, Anthropic, or Google API costs — those are separate.

**Trade-off vs. self-hosting your own server:** LiveKit Cloud costs more per minute at scale than running your own agent on Railway or Render, but the operational burden is dramatically lower. No Dockerfile optimization, no autoscaling configuration, no handling graceful shutdowns. For a product in its early growth phase, this is the right starting point.

### Path B: Hybrid — LiveKit Cloud for WebRTC, Self-Hosted Agent Workers

Keep LiveKit Cloud managing the WebRTC media layer (which you're already doing), and host your agent workers separately. Railway has an official LiveKit template and is the easiest option. Render also has official documentation. Kubernetes with the official manifests is the right choice at serious scale.

**Railway pricing for a persistent agent worker:**
- Hobby tier: $5/month minimum, usage-based at approximately $0.31 per vCPU per month and $0.10 per GB RAM per month. A small agent worker with 1 vCPU and 2 GB RAM costs roughly $1.50/month in compute.
- Scaling consideration: LiveKit recommends 4 cores and 8 GB RAM per agent server for production, handling 10–25 concurrent sessions. That's about $3.05/month on Railway Hobby — vastly cheaper than LiveKit's managed compute at scale, but you're managing the infrastructure yourself.

**The critical autoscaling rule:** When self-hosting, trigger scale-up at about 50% CPU load, even though the worker's own threshold to stop accepting jobs is 70%. This ensures new capacity exists before your current workers saturate. Scale-down cooldowns must be long — voice sessions last minutes to tens of minutes, and killing a worker mid-conversation means a disconnected user.

## Part 3: Fully Browser-Based End-User Experience

### What "Browser-Based" Actually Means for Osborn

Today, both the developer and the user must be on the same machine (or the same local network) because the agent runs locally. For a cloud product, you want the end-user experience to be entirely browser-based — they visit a URL, log in, start a session, and the agent connects from the cloud. The user never runs any local software.

This is entirely achievable. The architecture becomes:

```
User's Browser
    ↓ WebRTC (audio/video)
LiveKit Cloud (WebRTC relay)
    ↑ WebSocket (persistent, outbound)
Agent Worker (hosted on LiveKit Cloud OR Railway/Render)
    ↑ HTTPS
AI APIs (Anthropic, Google, OpenAI, Deepgram, ElevenLabs)
```

The frontend (Next.js on Vercel) handles auth, token generation, and the UI. The agent worker runs in the cloud and connects to LiveKit Cloud. The user's browser connects to LiveKit Cloud. No local software required on the user's end at all.

### The Session Browser Problem: Moving Sessions to the Cloud

Right now, `SessionBrowser.tsx` fetches sessions from `http://localhost:8741/sessions` — a local HTTP endpoint that reads JSONL files from the developer's working directory. In a cloud model, sessions need to live in a database.

The right move is Supabase. Each session gets a row in a `sessions` table. When the agent finishes a conversation, it writes the session metadata to Supabase via the REST API. The frontend queries Supabase directly — no more polling a local HTTP server. The `SessionBrowser` component drops the `agentUrl` field entirely and reads from `supabase.from('sessions').select(...)`.

## Part 4: Multi-Page State Model with Supabase

### Proposed Page Structure

The current app is a single page with a state machine (`browsing → waiting → connected`). Converting this to a multi-page model with Supabase auth gives each page a clear purpose and proper URL state.

**Recommended page structure:**

```
/ (root)
  → /login          — auth: email magic link or Google OAuth
  → /dashboard      — session list, "New Session" button, settings
  → /session/[id]   — reconnect to a specific past session
  → /room/[code]    — the live VoiceRoom UI (current VoiceRoom.tsx)
```

Each route from `/dashboard` onward is protected by Supabase auth middleware. The user's identity gates everything.

### The Auth Layer

The current package in `frontend/src/lib/supabase.ts` uses the old client-only pattern. For a multi-page auth model you need `@supabase/ssr` — the old `@supabase/auth-helpers-nextjs` is deprecated. Sessions get stored in HTTP-only cookies (not localStorage), which enables proper SSR.

The canonical middleware pattern goes in `middleware.ts` at the project root. Its job is to call `supabase.auth.getUser()` on every request, refresh the session token, write the refreshed cookie back, and redirect unauthenticated users away from protected routes. Critical rule: always use `getUser()` not `getSession()` in server-side code — `getSession()` reads the cookie without re-validating against the Supabase Auth server and was identified as unsafe in CVE-2025-29927.

For the auth UX itself, the simplest signup flow for a developer tool is Google OAuth plus email magic link. Both are one-click setups in the Supabase dashboard.

### Data Model in Supabase

Three core tables:

```
sessions
  id          uuid primary key
  user_id     uuid references auth.users (btree index required)
  room_code   text
  created_at  timestamptz
  last_message text
  message_count int
  metadata    jsonb

messages
  id          uuid primary key
  session_id  uuid references sessions
  user_id     uuid references auth.users
  role        text
  content     text
  created_at  timestamptz

uploaded_files
  id          uuid primary key
  session_id  uuid references sessions
  user_id     uuid references auth.users
  file_path   text
  file_name   text
  mime_type   text
  size        int
  created_at  timestamptz
```

RLS on all three tables with the same pattern:
```sql
-- SELECT
USING ((SELECT auth.uid()) = user_id)
-- INSERT
WITH CHECK ((SELECT auth.uid()) = user_id)
```

The `WITH CHECK` clause on INSERT policies is critical — without it, a user can insert rows with any `user_id` value, completely bypassing the isolation. Always wrap `auth.uid()` in a subselect `(SELECT auth.uid())` for per-statement caching — without this, Postgres evaluates the function once per row, which causes full table scans on large tables.

## Part 5: Agent Status Without LiveKit Polling (Supabase Realtime)

One of the clunkier parts of the current UX is the "waiting for agent" state — the frontend polls LiveKit room state to figure out whether the agent has joined. In a cloud model, you can replace this with Supabase Realtime Broadcast.

When the agent process joins a LiveKit room, it sends a status broadcast via Supabase's REST API:
```
POST https://<project>.supabase.co/realtime/v1/api/broadcast
{ channel: "agent-status:<session_id>", event: "status", payload: { status: "ready" } }
```

The browser subscribes to a private channel scoped to that session ID and updates the UI the moment the event arrives — no polling. The "waiting" state UI becomes a real-time push notification rather than a timeout-based check.

**Realtime limits:** Free plan supports 200 concurrent connections; Pro plan (which at $25/month you'll want for production) supports 500. Message size limit is 1 MB. Private channels require an RLS policy on the `realtime.messages` table.

## Part 6: The Signup Flow and Onboarding Design

### The Core Challenge: Two-Sided Installation

Osborn has a unique constraint: the AI agent needs access to the user's local filesystem to actually code. A fully cloud-hosted agent can do a lot — it can use Smithery MCP servers for GitHub, web search, etc. — but it cannot read or write files on the developer's machine without a local component. This creates a two-sided setup:

1. **Cloud side (zero-setup):** The Osborn web app, auth, session history, and optionally a cloud agent for tasks that don't require local file access.
2. **Local side (one-time install):** The `osborn` CLI/daemon that runs on the developer's machine, gives the agent access to the local filesystem, and connects to LiveKit Cloud.

The onboarding flow should walk users through both, clearly explaining why the local install is needed and making it as painless as possible.

### Proposed Onboarding Flow (Multi-Step)

**Step 1 — Sign Up (pure browser)**
- User visits osborn.app, clicks "Get Started"
- Signs in with Google or email magic link via Supabase Auth
- Account created, redirected to dashboard

**Step 2 — Dashboard (empty state)**
- Dashboard shows an empty sessions list
- Prominent "Start Coding" card at the top with a setup prompt
- Two options clearly presented: "Use Cloud Agent" (limited, no file access) or "Connect Local Agent" (full capabilities)

**Step 3a — Cloud Agent Path (zero install)**
- User clicks "Use Cloud Agent"
- A new session starts; the cloud-hosted agent joins via LiveKit
- Capabilities shown upfront: web research, GitHub via MCP, code generation — but explicit note that it cannot read or write files on your local machine
- Good for mobile, good for planning sessions, good for onboarding trial

**Step 3b — Local Agent Path (full capabilities)**
- Step-by-step installation guide rendered inline in the dashboard:
  1. Shows system requirements (Node.js 18+) with a check badge if detected via a test API call, or install link
  2. Copy-to-run install command: `npm install -g osborn-agent`
  3. Copy-to-run API key setup command
  4. Shows a "Connect" button that generates a one-time setup token and provides the command: `osborn connect --token <token>`
  5. The page polls (or uses Supabase Realtime) for the agent to connect and show the green "connected" badge
- Once connected, the page transitions to the active session UI

**Step 4 — Active Session (familiar UI)**
- VoiceRoom UI renders as it does today
- Session is saved to Supabase automatically
- Dashboard shows the session in history after it ends

### The Setup Token Pattern

Instead of asking users to manually copy their LiveKit credentials into a `.env` file, generate a short-lived one-time setup token on the server. The local agent CLI receives this token, fetches the full credential set from the Osborn API, stores them locally (in `~/.osborn/credentials.json`), and then connects. The user never sees raw API keys. The token expires in 5 minutes and can only be used once.

### Phase 2 — Database Schema & RLS

**Three database actions run in the Supabase SQL Editor:**

**Sessions table** replaces the JSONL files on local disk read via `http://localhost:8741`. Columns: `id`, `user_id` (references `auth.users`), `room_code`, `session_sdk_id` (the Anthropic Claude SDK's UUID), `voice_arch`, `provider`, `last_message`, `message_count`, `created_at`, `updated_at`. Two indexes: on `user_id` (required for RLS performance) and on `(user_id, updated_at desc)` for the dashboard query.

RLS policies follow the verified pattern with subselect caching:
```sql
USING ((SELECT auth.uid()) = user_id)
WITH CHECK ((SELECT auth.uid()) = user_id)
```
The `WITH CHECK` on INSERT/UPDATE is non-optional — without it, users can insert rows with arbitrary `user_id` values.

**Setup tokens table** for the one-time agent provisioning flow: `token` UUID (unique index with `WHERE used = false`), `user_id`, `data` JSONB (holds the secrets payload), `expires_at` (default 10 minutes), `used` boolean. An atomic `claim_setup_token()` Postgres function uses `FOR UPDATE` row-level locking to prevent double-claim race conditions, then marks the token used and returns the data JSONB.

**Storage RLS**: Make `osborn-uploads` private with `UPDATE storage.buckets SET public = false`. Add four policies on `storage.objects`: INSERT uses `storage.foldername(name)[1] = auth.uid()::text` (requires upload paths to start with the user ID folder), SELECT/DELETE/UPDATE use `owner_id = auth.uid()::text`. Replace all `getPublicUrl()` calls in `lib/supabase.ts` with `createSignedUrl(path, 3600)`.

### Phase 3 — Secure LiveKit Token API

The current `/api/token/route.ts` has two problems: no authentication check, and `participantName = user-<timestamp>` which is anonymous and arbitrary. Both are fixed here.

**Add auth gate:** `const { data: { user } } = await supabase.auth.getUser()` → return 401 if not authenticated. This requires importing `createClient` from the new `utils/supabase/server.ts`.

**New identity and room name:**
- `identity = user.id` — Supabase UUID as the LiveKit participant identity. Because identity must be unique per room in LiveKit (same identity connecting twice disconnects the first), using `auth.uid()` creates a 1:1 cryptographic binding between the Supabase user and the LiveKit participant.
- `roomName = osborn-${user.id}-${roomCode}` — encodes the user ID in the room name. The token's `room` grant field locks the token holder to exactly this room name. A user who somehow intercepts another user's room code cannot join that room because their token would be minted for a different room name.

Pass `userId: user.id` in the participant metadata JSON so the agent can extract it for Supabase writes and Realtime broadcast.

### Phase 5 — Onboarding Page + Setup Token Flow

The onboarding page (`/onboarding`) is a multi-step client component with this flow:

**Step 0 — Choose path:** "Cloud Agent" (skip to Step 4, no install) or "Local/Custom Agent" (continue to Step 1). The cloud path is appropriate for research and code generation without local file access. The local path enables full file system access.

**Step 3 — Connect (the key step):** The frontend calls `POST /api/setup-token`. This route is protected — it checks `supabase.auth.getUser()` before creating the token row. The page displays:
```

```

The CLI writes them to `~/.osborn/.env` and starts the agent.

The agent, on startup, broadcasts `{ status: "agent_connected" }` to Supabase Realtime channel `setup:<user_id>`. The onboarding page subscribes to that channel and shows success — then navigates to `/dashboard`.

### Phase 6 — Supabase Realtime Agent Status

The current "waiting for agent" UI in `page.tsx` (lines 135–163) tells the user to run a command and polls by watching for the LiveKit participant `osborn-agent` to join the room. This is replaced with a Supabase Realtime push.

**Agent side** — new `broadcastAgentStatus()` function in `agent/src/index.ts`: After `session.start()` resolves and `agent_state_changed` fires with `newState === 'listening'`, the agent POSTs to:
```
POST https://<ref>.supabase.co/realtime/v1/api/broadcast
apikey: <service_role_key>
Authorization: Bearer <service_role_key>

{ "messages": [{ "topic": "agent-status:<userId>:<roomCode>", "event": "status", "payload": { "status": "ready" } }] }
```
Both the `apikey` header and `Authorization: Bearer` header are required — Supabase's REST broadcast endpoint requires both. The `service_role` key is used (not `anon`) because server-side broadcast to private channels requires bypassing RLS.

**Browser side** — in the room page, subscribe to `agent-status:<userId>:<code>` as a private channel. When `status === "ready"` arrives, clear the waiting state and show the full VoiceRoom UI. No polling. No LiveKit participant detection.

Fallback: 30-second timeout → show error card with "re-run the connect command" instructions and a retry button.

### Phase 7 — Agent Writes Sessions to Supabase

After each `assistant_result` event fires in `index.ts`, the agent upserts to `public.sessions` via Supabase REST:

```
POST https://<ref>.supabase.co/rest/v1/sessions
Prefer: resolution=merge-duplicates,return=minimal
apikey: <service_role_key>
Authorization: Bearer <service_role_key>

{ user_id, room_code, session_sdk_id (from currentLLM.sessionId), last_message, message_count, updated_at }
```

The `user_id` comes from the participant metadata in the LiveKit join event (set in Phase 3 as `userId: user.id`). The `session_sdk_id` comes from the `session_id` event already tracked via `currentLLM.events.once('session_id', ...)`.

Once Supabase session writes are validated, `startApiServer()` in `index.ts` is removed (or kept as a lightweight health endpoint only, since Railway/Fly.io may use it for healthchecks).

## Page Sequence

```
/welcome → /login → /callback → /setup (5 steps) → /room/[code]
```

The `/welcome` page lives in a new `(public)/` route group — no auth required. It's your marketing entry point. Logged-in users are immediately redirected to `/dashboard`.

## The 5 Setup Steps at `/setup`

**Step 1 — node_check:** User runs `node --version` in their terminal, pastes the result into a text field. Frontend validates it against the regex `/^v(1[8-9]|[2-9]\d)\./` — matches Node 18+ only. Green check on success, error message with a link to nodejs.org on failure. Auto-advances after 500ms.

**Step 2 — install:** Two tabs: clone from GitHub OR download a ZIP. GitHub tab shows `git clone` + `cd osborn/agent` + `npm install`. ZIP tab has a download button (server-side auth-gated route `GET /api/download-agent`) and the same install instructions. Two manual checkboxes — the user confirms they've done both. No automated verification because npm output varies. This is the step where `agent/bin/cli.js` and all agent dependencies land on the user's machine.

**Step 3 — env_config:** Shows a copyable `.env` template. The template is the `agent/.env.example` contents plus `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. LiveKit credentials are pre-filled if stored in `profiles`. Per-key collapsible "Where do I get this?" tooltips with direct links — LiveKit Cloud dashboard, Google Cloud Console, platform.openai.com, etc. One checkbox: "I've saved my `.env` file." Key connection to existing code: `agent/src/index.ts` line 1 runs `import 'dotenv/config'` — it loads this `.env` file before any other import.

**Step 4 — connect:** This is the real-time confirmation step. Frontend calls `POST /api/setup-token` (authenticated, protected route) → gets a UUID token with a 10-minute expiry. Displays:
```
node bin/cli.js connect --token <uuid>  [COPY]
```
The user runs this in their terminal from the `osborn/agent/` directory. The CLI's new `connect` subcommand:
1. Posts to the **unauthenticated** `/api/claim-token` endpoint (token is the auth mechanism)
2. Gets back LiveKit + Supabase credentials
3. Appends them to the local `.env` file
4. Broadcasts `setup:<user_id> → agent_connected` event via Supabase Realtime REST API using the service_role key
5. Then starts `tsx src/index.ts` — the actual agent process

Meanwhile the browser is subscribed to the `setup:<user_id>` Supabase Realtime channel. When it receives `agent_connected`, it shows "✅ Agent connected!" and enables the Continue button. A 10-minute countdown and "Get a new token" fallback handle expiry.

**Step 5 — complete:** PATCHes `profiles.setup_completed = true`. Calls `/api/token` for the first LiveKit room JWT. Navigates to `/room/<code>`.

## How the Real-Time Connection Works

Three layers of confirmation:

1. **Setup token claim** — CLI-to-browser signal via `setup:<uid>` Realtime channel. Confirms the agent process started and has valid creds.

2. **LiveKit room join** — The existing `ParticipantConnected` handler in `index.ts` at line 1266. No changes needed — this fires when the browser joins the room.

3. **`broadcastAgentStatus()` from `index.ts`** — New function, called after `session.start()` resolves and the agent enters listening state. Uses the Supabase Realtime REST broadcast endpoint with both `apikey` and `Authorization` headers (both required). Channel name: `agent-status:<uid>:<code>`. Browser subscribes to this in the `/room/[code]` page — when `status: 'ready'` arrives, the "waiting for agent" spinner clears and the microphone enables.

The `userId` flows into the agent from `participant.metadata.userId`, which is embedded in the LiveKit JWT by `/api/token` after the Phase 3 auth gate changes.
