# Critical Patterns

Bug fixes and gotchas accumulated from production incidents. Referenced from `CLAUDE.md` to keep the top-level claude guidance under the 40k context budget. Read this when debugging anything involving persistent sessions, voice queue timing, Gemini quirks, or research flow.

- **Self-healing CWD fallback chain**: `index.ts main()` walks `[OSBORN_CWD env, config.workingDirectory, process.cwd()]` and picks the FIRST entry whose path actually exists on disk. Blindly trusting any of these has bitten us — e.g. cloud sandboxes had `OSBORN_CWD=/root/workspace` baked in but `/root` is `drwx------` and the dir doesn't exist, so the SDK's `child_process.spawn(node, [cli.js], { cwd })` errored ENOENT and reported the misleading "Claude Code executable not found at .../cli.js". `process.cwd()` is the ultimate safety net — it exists by definition.
- **`killCurrentLLM(reason)` MUST be called before nulling `currentLLM`**: The persistent ClaudeLLM session is deliberately kept alive across user messages to avoid JSONL replay. When the participant disconnects, simply nulling the JS reference does NOT kill the underlying Claude Code subprocess — the SDK keeps draining `MessageChannel`, running tools, capturing checkpoints, and pushing TTS into a now-null voice session. Visible as repeated `⚠️ tts_say fired but currentSession is null — text dropped`. The fix is `killCurrentLLM(reason)`, which duck-types `abortQuery()` (on `ClaudeLLM`) or `abortAgent()` (on `PipelineDirectLLM`) — both call `closeSession()` which kills the subprocess. Required at all three cleanup sites: `Disconnected` event, `previous_session_cleanup` (when a new participant joins while an old one is still around), and `participant_disconnected`.
- **opts sync**: When updating ClaudeLLM state (`setResumeSessionId`, `setContinueSession`, `resetForSessionSwitch`), always sync to both the instance field AND `this.#opts` — otherwise `ClaudeLLMStream` won't see the update.
- **Workspace path fallback**: `sessionId` for workspace path uses `this.#sessionId || this.#opts.resumeSessionId || null`. When null (first query of new session), workspace instructions are omitted from the system prompt. Workspace is created when the SDK emits the real `session_id`. For resumed sessions, workspace is eagerly created since the real ID is already known.
- **Workspace write auto-approval**: The `canUseTool` callback auto-approves `Write`/`Edit` calls when the file path contains `/osb/`, `.osborn/sessions/`, or `.osborn/research/`. This prevents the SDK permission prompt from blocking workspace writes. The `PreToolUse` hook remains as a safety net to block writes outside the workspace. The system prompt has strict rules: always use full absolute workspace path, never hallucinate paths, never claim a write without actually calling Write/Edit.
- **Configurable model**: `ClaudeLLMOptions.model` defaults to `claude-sonnet-4-6`. Passed to both the `model` getter and SDK `Options.model`. Haiku was tested but hallucinated file structures; Sonnet is the safe default.
- **Unified voice injection queue**: ALL system injections (research updates, completions, notifications, errors) go through `voiceQueue[]` + `queueVoiceInjection()` + `processVoiceQueue()`. Never call `generateReply` directly for injections. The queue only processes when `agentState === 'listening'`. Multiple items are batched into one `generateReply({ instructions, toolChoice: 'none' })` call. The `agent_state_changed` → `listening` event triggers `processVoiceQueue()` again after the model finishes speaking.
- **Voice announcements in realtime mode**: Use `queueVoiceInjection()` (which gates on model availability) not `session.generateReply()` directly, and not `session.say()` (no standalone TTS in realtime). Use `[NOTIFICATION]` prefix + "Do NOT call any tools" to prevent feedback loops.
- **Feedback loop prevention**: Never pass system messages through `generateReply({ userInput })` in realtime — Gemini/OpenAI treats them as new user requests. Use dedup guard (`lastTaskRequest`/`lastTaskTime` with 10s window).
- **ReactMarkdown**: Must receive content as children (`<ReactMarkdown>{content}</ReactMarkdown>`), not self-closing.
- **extractTextContent()**: Use this helper (in `config.ts`) when reading conversation history to avoid dumping raw tool_use/tool_result JSON.
- **PostToolUse must emit `input`**: The `PostToolUse` hook emits `tool_result` events with `{ name, input: input?.tool_input || {} }`. The `input` field is required — `index.ts` checks `data.input?.file_path` to detect session workspace writes (`/osb/`, `.osborn/sessions/`, or `.osborn/research/`).
- **Non-blocking `ask_agent`**: The `ask_agent` tool returns immediately ("Research started...") and runs Claude research in the background via `executeResearch()` (extracted function). Progress updates are queued in `activeResearch.pendingUpdates`, debounced by `scheduleResearchBatch()` (8s), and pushed to the unified `voiceQueue`. Final results are pushed via `queueVoiceInjection('[RESEARCH COMPLETE] ...')`. The Claude SDK has an internal queue — when `query()` is called while another is running, it enqueues with `queue-operation` events and waits. Each `query()` produces assistant messages with distinct `requestId` values in the JSONL. The SDK auto-resumes via `sessionId` — follow-up tasks inherit all prior research context. **IMPORTANT**: Do NOT abort old research when new research starts — let the SDK queue handle it. Old research completes naturally, results land in JSONL, fast brain can read them. Only abort on disconnect/cleanup.
- **JSONL research tracking**: Each `query()` call produces messages with unique `requestId` values. User text messages establish conversation branches via `parentUuid` chains. `queue-operation` events (`enqueue`/`dequeue`/`remove`) track the SDK's internal task lifecycle. Sub-agents spawned via `Task` tool get their own `agent-id` in enqueue content. These fields can be used to identify which research task produced which output.
- **Parallel sub-agents**: The research system prompt instructs the Claude agent to use the `Task` tool for parallel work. Multiple Task calls in the same response spawn concurrent sub-agents (e.g., researching 3 topics simultaneously). Sub-agents can use Read, Glob, Grep, Bash, WebSearch, WebFetch. This dramatically speeds up research that would otherwise be sequential.
- **Voice queue `isProcessingQueue` guard**: Prevents concurrent `generateReply` calls. Set `true` before calling `generateReply`, cleared on every `agent_state_changed` event. On error, items are dropped (not re-queued) to prevent infinite retry cascades. A 15s safety timeout auto-clears the guard if `agent_state_changed` never fires (e.g. Gemini state machine hang). The queue retry delay after `listening` state is 500ms (not 50ms) to let the model settle.
- **Gemini voice injection — AsyncLocalStorage fix**: The LiveKit SDK's `asyncLocalStorage` (in `agent_activity.ts:970-973`) auto-forces `toolChoice='none'` when `generateReply` is called inside a tool execution context. `setTimeout` callbacks inside `askFastBrainTool.execute()` inherit this context. Gemini ignores `toolChoice:'none'`, calls tools anyway, but the SDK drops the call at `generation.ts:845-853`, leaving Gemini stuck. **Fix**: `processVoiceQueue()` passes `toolChoice: 'auto' as any` explicitly for Gemini, overriding the SDK's auto-`'none'`. The SDK check `if (toolChoice === undefined)` skips because toolChoice is defined. There is no way to break out of an `AsyncLocalStorage` context you don't own — `setTimeout`, `setImmediate`, `process.nextTick`, `Promise.then` all propagate it.
- **Gemini "." phantom input**: When Gemini receives `generateReply({ instructions })`, it sometimes generates a `"."` as a pseudo-user-input and routes it through `ask_fast_brain`. This is NOT a mechanism we built — it's Gemini's own interpretation of system instructions as a user turn. The injection bypass guard in `askFastBrainTool.execute()` handles `[SCRIPT]`/`[PROACTIVE]`/`[NOTIFICATION]` prefixes; `"."` falls through to the fast brain which returns a brief response.
- **Gemini `interrupt()` constraint**: Never call `session.interrupt()` for Gemini provider — it disrupts the internal state machine, causing the model to hang in `speaking` state indefinitely (no transition back to `listening`). All `interrupt()` calls in `processVoiceQueue()` and `user_text` handler must be guarded with `if (currentProvider !== 'gemini')`. Gemini handles interruptions internally via `activityStart`/`activityEnd`.
- **Smithery proxy for cloud MCP**: Claude Agent SDK's `type: 'http'` transport has a bug (#18296) that forces OAuth on all HTTP servers. Smithery servers are connected via in-process proxy (`smithery-proxy.ts`) using `createSmitheryProxy()` which returns `type: 'sdk'` config. The proxy uses `@smithery/api/mcp` `createConnection()` for the working transport. The proxy patches both `McpServer.connect` and `Server._server.connect` to handle reconnection across SDK `query()` calls.
- **Research event batching**: During background `ask_agent` execution, `onToolUse` generates enriched entries with tool parameters (file paths, commands, search queries, hostnames) and pushes to both `researchLog` and `pendingUpdates`. `onToolResult` only pushes to `researchLog` (not `pendingUpdates`) to avoid "Read done" doubling. `scheduleResearchBatch()` debounces (8s), routes batch through `contextualizeResearchUpdate()` (fast brain generates natural 1-2 sentence voice update from raw events), and pushes to `voiceQueue` via `getResearchUpdateInjection()`. Capped at 3 voice updates per task via `voiceUpdateCount`. The update prompt tells the voice model NOT to say "complete" or "done". Final result includes research log + 4000-char findings.
- **Proactive conversational loop**: `startProactiveLoop()` runs a 15-second interval during research that calls `generateProactivePrompt()` (fast brain) to generate things for the voice model to say — open questions from spec, discussion of findings, progress with depth. Capped at 4 prompts per task (`MAX_PROACTIVE_PROMPTS`). Guards: only fires when `agentState === 'listening'`, `userState !== 'speaking'`, no batch timer active, no queue processing. `stopProactiveLoop()` called in all cleanup paths (research completion, error, disconnect, reconnect, recovery).
- **Visual document generation**: `generateVisualDocument()` in fast-brain creates structured markdown documents (comparison tables, Mermaid diagrams, analysis, summaries) from research context. Registered as `generate_document` tool on the realtime model. Reads spec + JSONL results, writes to workspace, notifies frontend via `research_artifact_updated`.
- **SWC parser quirk**: Next.js SWC parser chokes on `> 0` inside template literals in JSX `className`. Use truthy checks (`arr.length` not `arr.length > 0`) in template expressions.
- **`haikuInFlight` guard**: Tracks whether `ask_fast_brain` is in flight. While set, the unified voice queue holds (does not call `generateReply`) — otherwise the fast brain's tool response races our injection and Gemini drops one. The guard clears in both the success and error paths of the tool's `execute()`, after which `processVoiceQueue()` is called with a 500ms delay.
- **Realtime mode has only TWO tools**: `ask_fast_brain` and `respond_permission`. There is no `ask_agent`, `ask_haiku`, `read_spec`, or `generate_document` tool registered on the realtime LLM — all of those routings live INSIDE `askFastBrain()`. The fast brain returns a script string which the model speaks verbatim. If the fast brain decides research is needed, it appends `NEEDS_DEEPER_RESEARCH` markers and the `triggerResearch` callback fires `executeResearch()` in the background; the script the model speaks is a contextual acknowledgment from `generateResearchAck()`.
- **Injection bypass in `ask_fast_brain`**: When Gemini receives a system injection via `generateReply({ instructions })`, it sometimes calls `ask_fast_brain` with the injection content as the "question". The tool's `execute()` matches `[SCRIPT]`, `[PROACTIVE]`, and `[NOTIFICATION]` prefixes and returns the content directly without round-tripping through the fast brain. For OpenAI this is a fallback (it normally speaks instructions directly with `toolChoice: 'none'`); for Gemini this is the intended path.
- **Pipeline `emergency_stop`**: The pipeline fast brain (`pipeline-fastbrain.ts`) has an `emergency_stop` AFC tool that the Gemini observer calls when the user clearly wants to abort a destructive action ("stop", "wait no", "cancel"). It calls `agentControl.abort()` to kill the Claude subprocess, then `agentControl.sendPrompt()` with an `[EMERGENCY STOP]` prompt that includes the user's recent messages and a snapshot of recent activity. **Never trigger for**: research, reading, exploring, searching — only destructive/altering actions. Priority is destructiveness > signal strength.
- **`updateSpecFromJSONL()` post-research flow**: After `ask_agent` completes, fires `updateSpecFromJSONL()` as fire-and-forget. Reads FULL untruncated data from Claude JSONL via `getRecentToolResults()` (30 results), `readSessionHistory()` (50 messages), and `getSubagentTranscripts()`. Fast brain consolidates into spec.md. On completion, notifies frontend via `research_artifact_updated`.
- **`getSpecForVoiceModel()`**: Reads spec.md and truncates to a budget for injection into the realtime voice model's context. Truncates at section boundaries.
- **`parseChunkResponse()` multi-strategy parser**: Handles LLM output that may contain code blocks, control characters, or raw markdown. Strategies: direct JSON.parse → control char stripping → regex spec extraction → raw markdown detection.
- **Bidirectional question tracking**: spec.md `Open Questions` section has subsections `From User` and `From Agent`. Fast brain tracks which questions are answered and marks them done with checkboxes.

## Sprites cloud-sandbox patterns (added v0.8.30–0.8.38)

- **Unique sprite names per `createSandbox`**: `generateUniqueSpriteName(userId)` appends a base36 timestamp suffix (e.g. `osborn-1b9d70e5-2a4-lszt8q`). Each new sprite gets a fresh name. Sprites' API gateway has been observed to develop "stuck routing" entries per sprite name — once a name has failed registration from a given source IP, subsequent PUTs from that IP keep returning 503 even after delete+recreate under the same name. Fresh names sidestep this. `findUserSandbox(userId, knownSandboxId?)` accepts the Supabase-stored ID as source of truth; deterministic name (`spriteNameFromUserId`) is fallback only for legacy users with no Supabase entry. ALL `/api/sandbox` callers pass `await getKnownSandboxId()`.
- **Restart service on warm-wake (CRIU + LiveKit reconnect)**: When `startSandbox()` sees `sprite.status === 'warm' || 'cold'` AND the existing service has marker bootstrap, it `restartService(sandboxId)` — kills + restarts the agent process. Necessary because CRIU snapshot preserves the agent's local socket state but LiveKit Cloud's server-side has long since evicted the agent (TCP timeout). The frozen process resumes with a "ghost" WebSocket; user joins room, agent never sees them. Service restart gives a fresh agent process with a fresh LiveKit connection, while preserving the container overlay (OAuth credentials, JSONLs intact).
- **Never restore checkpoint on transient API failure**: `startSandbox()` Step 2 tracks `serviceCheckSucceeded` separately from `bootstrapHasMarker`. The bare catch on `GET /services/osborn` used to silently swallow 503s, leave `bootstrapHasMarker = false`, and proceed to `restoreCheckpoint()` — wiping the overlay (OAuth + JSONLs). Now: only restore when we KNOW the service genuinely lacks marker logic, never on uncertainty. Restore is destructive; treat it like `rm -rf`.
- **PUT idempotency**: `PUT /v1/sprites/<name>/services/osborn` is a no-op when the cmd matches — returns 200 with body `"Service already running with that command, use POST .../restart"`. Safe to retry. Different cmd requires a `STOP + DELETE + PUT` cycle.
- **Sprites does NOT soft-delete**: Verified empirically (probed `/sprites/<id>/undelete`, `/restore`, `/recover`, `/revive`, `/recreate`, plus `?include_deleted=true`, `?status=deleted`, `?archived=true` — all 404). Once deleted, the overlay, persistent disk, and ALL checkpoints are unrecoverable. The dashboard delete button uses a two-click confirm pattern (`deleteArmed` state, 4s timeout to disarm) because of this.
- **Pre-restore checkpoint mechanic**: When `restoreCheckpoint(<targetId>)` is called, Sprites first auto-creates a `pre-restore-v<N>-<unix-timestamp>` snapshot of the current overlay. These accumulate forever. `startSandbox()` filters them out of restore candidates (`cp.id.startsWith('pre-restore-')`) because they often capture mid-corruption states. They are useful for manual recovery of a wiped sprite — content can be inspected via the fs API at `/.sprite/checkpoints/<id>/...` (per docs, "Last 5 mounted") although in practice this mount is sometimes empty.
- **fs API ≠ container view**: Sprites uses CRIU + an overlay-style filesystem on `/home`. The fs API (`/v1/sprites/<id>/fs/list|read|write`) reads the persistent disk. The running container reads through the overlay (the CRIU snapshot's base + current process writes). They can desync. Most painfully: a checkpoint restore can roll the overlay base back to a state that pre-dates files which still exist on persistent disk — so the agent's `readdirSync('/home/sprite/.claude/projects/...')` shows fewer JSONLs than the fs API does. The 0.8.37 bootstrap inventory log + frontend `consistency-check` action surface this divergence as a dashboard banner.
- **`fs/write` returns 405**: The Sprites fs API exposes `GET /fs/list`, `GET /fs/read`, but `POST /fs/write` is 405 Method Not Allowed. `PUT /fs/write?path=...` works (returns 200 with `{path, size, mode}`). However, writes via fs API land on the persistent disk layer, NOT the container's overlay — so the running container does NOT see them at the same path. Bidirectional fs sync between layers is not provided.
- **`process.cwd()` is the user's launch dir, NOT the package dir**: In production cloud, osborn is launched with `OSBORN_CWD=/home/sprite/workspace`. Static files shipped with the package (e.g. `meeting-output.html`) must resolve via ESM `__dirname` (`fileURLToPath(import.meta.url)` + `dirname`), never `process.cwd()`. The `meeting-output.html` handler tries 3 candidates: `__dirname/meeting-output.html` (post-build, from `dist/`), `__dirname/../src/meeting-output.html` (dev with compiled JS), `__dirname/../meeting-output.html` (tsx run from src). Build script copies the file to `dist/` so it ships with the npm package: `cp src/meeting-output.html dist/`.
- **Recall.ai bot payload field names**: `recording_config.transcript` is a **dict** not a bool — omit it entirely if `transcription_options` is set. `output_media.camera.kind` is the field name (NOT `type`). Acceptable values: `'webpage'` or `'default'`. Recall returns 400 with explicit field error messages if either is wrong; the bot is never created and `joinMeeting` throws.
- **Recall.ai region**: `RECALL_REGION` env var selects the regional endpoint (`us-east-1`, `us-west-2`, `eu-central-1`, `ap-northeast-1`). Default is `us-west-2`. If your API token belongs to a different region, every API call returns 401 with a region-mismatch detail message. Forwarded into sprites via `getPlatformEnvVars`.
- **CRIU + WebSocket lifecycle (open issue, no agent-side fix yet)**: When a sprite hibernates, the agent's TCP/WebSocket sockets are snapshotted in their local state, but the remote peer (e.g. LiveKit Cloud) keeps its own connection state and times out independently. On wake, only HTTP requests cause the sprite to thaw — and even then, only the HTTP server thaws; the agent's event loop stays paused unless something feeds it (a request hits its own paths, or the runtime itself nudges it). Result: agent's in-memory state says "Connected to room", but LiveKit has evicted it. The 0.8.38 frontend fix (restart service on warm-wake-with-marker) papers over this from outside. A proper agent-side fix would be a watchdog that detects LiveKit `Disconnected` events and reconnects in-place — not yet implemented.

## Room-presence lifecycle, idle-exit billing & meeting transcript (added v0.9.49–0.9.94)

- **Summary-index watcher retains the whole LLM graph — stop it before dropping the reference**: `killCurrentLLM()` originally only aborted the SDK subprocess. The `PipelineDirectLLM` summary-index watcher is a 10s `setInterval` whose closure retains the entire `PipelineDirectLLM → ClaudeLLM` object graph, so the graph was never GC'd. Repeated reconnects (e.g. 15 from a frontend redeploy) leaked 15 timers + 15 retained graphs, each re-reading JSONL every 10s, until node OOM'd (~980 MB). Fix: `killCurrentLLM()` duck-types `stopIndexWatcher()` and calls it BEFORE aborting. (0.9.51)
- **The agent held LiveKit rooms open forever and billed 24/7**: agent used to eager-connect on boot and hold the room for the machine's whole life; with only the agent present LiveKit never considers the room empty, so it never closes — one forgotten session burned 25h of connection-minutes. Fix: room-presence lifecycle — agent LEAVES when no user is present (agent-side "alone" timer, tab-close-proof — does not depend on frontend JS still running — plus explicit POST `/leave-room`) and rejoins via POST `/connect-room`. (0.9.52)
- **Idle machine kept billing after a clean leave; `process.exit(0)` is the stop signal**: after an intentional alone-leave the agent sat "idle, awaiting /connect-room" forever with the Fly machine `started`, billing 24/7. Confirmed twice (a zombie WS held 5,700+ min "In progress" on LiveKit; a $123.61 July invoice showed two 4GB machines running the whole cycle). Because the restart policy is `on-failure`, `process.exit(0)` cleanly STOPS the machine (billing stops, volume + JSONL persist) and the next Resume boots it. Armed on `livekitState.status → 'idle'` with a 10-min grace; re-checks still-idle before exiting. Never fires in local dev (no `FLY_APP_NAME`); override `OSBORN_IDLE_EXIT=0`. (0.9.73)
- **Ghost agent: process alive, room dropped, `/health` lied**: agent could lose its LiveKit room while the process stayed alive, and `/health` kept reporting `connected`. Fix: rejoin on `RoomEvent.Disconnected` and make `checkOsbornHealth` inspect `livekit.status`. Recurring theme across this window — never trust the event stream or in-memory `status` alone; poll actual room state. (0.9.49)
- **Zombie-watchdog must set state, not wait for the Disconnected event**: a zombie WS is precisely the case where `RoomEvent.Disconnected` never fires. After a watchdog forced-leave, `livekitState.status` stayed `connected`, so `/health` lied, `/connect-room` no-op'd, and the next user joined a room the agent wasn't in ("Connecting…" forever). Fix: the watchdog sets `status = 'idle'` immediately and arms the idle-exit timer as a backstop. (0.9.76)
- **`cpSync` stamps "now" and scrambles auto-resume ordering**: `cpSync` sets the destination mtime to the copy time. The frontend's auto-resume picks most-recent-by-mtime, so a sync import made a random tar-order file (often a tiny, months-old session) look newest — users kept "resuming" into the wrong session. Fix: `utimesSync` to preserve the source mtime. (0.9.75)
- **Sync clients that omit `targetWorkDir` write un-resumable sessions**: stale voice-native-sync clients wrote source slugs verbatim. Those sessions LIST fine but silently fail to RESUME — the SDK resumes at `cwd=workingDir`, whose slug they don't match. Fix: default `targetWorkDir` to the machine's own working directory. (0.9.74)
- **Room-code rotation raced clients across restarts**: a restart (common with idle-exit stop/start cycles) regenerated the room code; a client that fetched `/room-code` just before the restart joined a room the rebooted agent never created → stuck "Connecting…". Fix: persist the room code to `~/.osborn/room-code` (on the volume) and reuse it across restarts. (0.9.77)
- **Transient LiveKit drops must NOT make the agent leave its room**: binding the explicit-leave `disconnect()` (POST `/leave-room`) to the `<LiveKitRoom>` `onDisconnected` lifecycle event meant every transient drop (network blip, tab-visibility change, mobile background pause) kicked the agent out of the room the user was reconnecting to. Fix: two paths — `disconnect()` (explicit Leave, POSTs `/leave-room`) vs `disconnectFromLiveKitLifecycle()` (any LiveKit drop → capture log + navigate only, never `/leave-room`). (0.9.58)
- **Stale/racing `/leave-room` kicked out the current user mid-adopt**: a previous client's teardown landing after a new client joined kicked the agent out while adopting the new user. Fix: `/leave-room` is a no-op when `room.remoteParticipants.size > 0`; the alone-timer handles the real departure. (0.9.79)
- **`ParticipantConnected` only fires for participants who join AFTER the agent (join race)**: if the user's browser won the race, they were already in the room when the agent joined and the event never fired. Fix: after `connectWithRetry()`, `/connect-room` adopts pre-existing participants. (0.9.76)
- **The same Room stops delivering events after a leave/rejoin — and synthetic `room.emit()` doesn't reach rtc-node listeners**: after a leave/rejoin cycle the same `Room` instance could stop delivering `ParticipantConnected`. First fix (0.9.80): 5s adopt-poll re-emitting the event — but `(room as any).emit(...)` does NOT reach rtc-node's Room listeners, so nothing happened. Real fix (0.9.81): extract the handler to a named reference and CALL it directly. Ultimate fix (0.9.83): a fresh `Room` instance per session — rtc-node's `removeAllListeners` on leave leaves the reused Room permanently deaf.
- **Fresh suffixed room per `/connect-room` breaks the old `/room-code` token flow**: with temporary rooms, each `/connect-room` creates a fresh suffixed room and returns its `roomName`. Minting the LiveKit token from the stale `/room-code` value joined the wrong room → stuck "Connecting…". Fix: mint the token from the `roomName` that `/connect-room` returns; fall back to `/room-code` for older agents. (0.9.83)
- **Recall live transcript: batch `download_url` only populates post-meeting; partials carry the live data**: the batch transcript `download_url` is empty during the call and only populates after it ends — live transcript requires Recall `realtime_endpoints` webhooks. Additionally, low-latency streaming emits `transcript.partial_data` DURING the call (finals lag); the old code dropped all partials. Fix: accept `partial_data` with dedup, and log every webhook receipt (event + word count). (0.9.84, 0.9.86)
- **Meeting file/transcript work exceeds the 3-tool-call budget — delegate to the writer sub-agent**: the main orchestrator has a hard PreToolUse limit of 3 direct tool calls per turn. Writing `meeting-todos.md` and pulling transcripts (curl + jq + Write) is far more than 3 calls, so doing it directly gets the agent blocked. Sub-agents are exempt. Fix: the `meetings` skill delegates ALL meeting file/transcript work to the `writer` sub-agent in ONE background `Task` call. (0.9.89)
- **The meeting canvas is one page acting as camera + mic + ears; resync on SSE reconnect**: with Recall `output_media`, a single webpage is streamed as BOTH the bot's camera and mic, and is granted mic access to the meeting audio. The page connects to `GET /canvas-stream` (SSE) for `say`/`show` commands. On reconnect the server resends the last `show` so a page reload doesn't blank the bot's camera. (0.9.87)
- **Playwright trace fails otherwise-passing e2e runs on a self-closed CDP browser**: `trace.zip` truncates when the CDP browser self-closes, failing runs that were otherwise green. Disabled in the scenario runner; video + audio + flight-log replays supersede it.
